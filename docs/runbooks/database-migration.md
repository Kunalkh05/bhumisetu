# Database Migration Runbook

## Overview
This runbook covers the procedures for managing Alembic database migrations
in the BHUMISETU platform. All schema changes must follow this process to
ensure data integrity and zero-downtime deployments.

## Prerequisites
- PostgreSQL 14+ with PostGIS extensions
- Python 3.11+ with `alembic` installed
- Access to the target database environment

## Creating a New Migration

```bash
# Navigate to API directory
cd bhumi-setu/apps/api

# Generate migration from model changes
alembic revision --autogenerate -m "describe_your_change"

# Review the generated migration
cat alembic/versions/<migration_id>_describe_your_change.py
```

## Applying Migrations

### Development
```bash
alembic upgrade head
```

### Staging / Production
```bash
# Always check current state first
alembic current

# Show pending migrations
alembic history --indicate-current

# Apply one migration at a time
alembic upgrade +1

# Verify
alembic current
```

## Rolling Back Migrations

```bash
# Roll back one step
alembic downgrade -1

# Roll back to specific revision
alembic downgrade <revision_id>

# Roll back to base (WARNING: destructive)
alembic downgrade base
```

## Best Practices

1. **Always review autogenerated migrations** — Alembic may miss
   index changes, constraints, or generate incorrect drop statements.

2. **Test migrations on a copy of production data** before applying
   to production.

3. **Keep migrations small** — One logical change per migration file.

4. **Never edit applied migrations** — Create a new migration instead.

5. **Include data migrations** when column semantics change (e.g.,
   splitting a name field into first_name and last_name).

6. **PostGIS extensions** must be created in the `public` schema before
   any spatial columns are added.

## Troubleshooting

### "Target database is not up to date"
```bash
alembic stamp head  # Only if you're certain the schema matches
```

### "Can't locate revision"
```bash
alembic history --verbose  # Check for broken chain
```

### Foreign Key Violations During Migration
Ensure data migrations run before schema changes that add constraints.

## Emergency Procedures

If a production migration fails mid-way:

1. **Do NOT retry** the migration immediately
2. Check `alembic_version` table for current state
3. Manually inspect the schema to understand partial application
4. Fix the migration script and create a corrective migration
5. Apply the fix after thorough testing
